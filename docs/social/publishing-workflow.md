## Weekly video run

1. Read the journal and Metricool’s existing scheduled/published posts. Determine the Saturday’s ISO week in Istanbul. If that week already has a successful or scheduled video for a platform, do not create another for that platform.
2. Select a useful, distinct topic. Rotate recruitment, international education, investment advisory and humanoid robotics. Prefer a concrete preparation question, service explanation or dated source-based development. Consult `channel-branding.md`; do not simply repeat the introductory advertisement every week.
3. Copy the weekly JSON template into that date’s output directory. Supply six short scenes and separate Instagram caption, YouTube title and YouTube description. Preserve the canonical website URL. Each scene is five seconds; 0.4-second dissolves produce a 28-second video. Photo, four-item list and closing layouts are supported. English or Turkish text is supported; use concise English onscreen text and bilingual caption by default. Existing Pillow font measurement rejects lines that would overflow.
4. Validate and render:

   ```sh
   python docs/social/render-weekly.py social/YYYY-MM-DD/topic.json --validate-only
   python docs/social/render-weekly.py social/YYYY-MM-DD/topic.json --output social/YYYY-MM-DD/topic.mp4
   ```

5. Run FFprobe, extract representative frames and view them. Confirm 720×1280, 28 seconds, H.264/AAC, legible text, intact full-colour logo, safe margins, correct website, no clipping and no factual overclaim. The original synthesized audio requires no external music licence. The renderer never modifies the source logo.
6. Resolve the completed MP4 to an **absolute local path** before calling Metricool. Schedule one Short and one Reel using their separate captions. Persist each platform result immediately; a failure on one must not cause a duplicate on the other.

## Daily Instagram card run

1. If Istanbul’s weekday is Saturday, skip this image task; the weekly Reel owns that slot. Read the journal and remote schedule before doing work.
2. Reuse the current feed from the existing 09:00 website news workflow. Check its schema, last-checked time, item publication date and primary-source URL. A recently checked feed can contain older articles: do not describe an older event as happening today.
3. Choose an unposted item and rotate categories. Open the primary source when refreshing or materially changing the summary. Preserve the distinction between an announcement, agreement, plan and completed implementation. Do not copy an article or scrape a publisher’s image. If the feed is unavailable, stale by more than 48 hours or has no eligible unposted item, record the reason and use an already prepared, sourced evergreen brief only if one exists; otherwise skip rather than invent a fresh update.
4. Make a short paraphrase in a copied daily JSON template. Record source URL, publisher, publication date, checked-at timestamp, item ID and bilingual Instagram caption. The visual headline and summary are concise; the caption carries the full HTTPS source link and date. Keep Instagram copy within the platform’s text limit.
5. Validate, then render a native vector card:

   ```sh
   python docs/social/render-daily-card.py social/YYYY-MM-DD/topic.json --validate-only
   python docs/social/render-daily-card.py social/YYYY-MM-DD/topic.json --output social/YYYY-MM-DD/topic.png
   ```

   The tool writes an editable SVG, 1080×1350 PNG and `.metadata.json` with source details, captions and SHA-256. Text is measured and rejected if it cannot fit; it is never silently truncated. The embedded logo bytes are unchanged. Dependencies are FFmpeg with its installed `librsvg` decoder and Pillow for text measurement. JPEG output is also available by choosing `.jpg` if a platform/tool requires it.
6. View the PNG, check the source/date/caption against the selected feed item, and pass its **absolute local path** to Metricool. Publish one Instagram image update, not a YouTube Short. Save the returned post identifiers and status in the journal.

## Deduplication, retries and durable state

The journal is updated by the publishing workflow, not the renderer. Use a stable slot key independent of file revisions: `weekly:2026-W41:youtube`, `weekly:2026-W41:instagram`, or `daily:2026-10-11:instagram`. Also store the content hash and source item IDs to avoid repeating the same news under a new filename.

Each entry should record: slot key, content type, topic/item IDs, source/provenance, asset path and SHA-256, caption text or its path/hash, platform/network, brand ID, scheduled local date/time and timezone, status, remote post ID/UUID, attempt timestamp and any error. Keep statuses distinct: prepared, submitted, scheduled, published, failed, skipped. A scheduled result is not proof of publication.

- Before creating a post, reconcile the journal with the remote calendar and recent posts. A prior timeout can still have created a remote post.
- Write each successful platform result immediately, then continue with the other platform. Retry only the failed platform.
- Never blindly recreate a post whose request outcome is unknown. Search by time, brand, caption and media first; record the remote ID if found.
- Serialize journal writes; use an atomic replacement and preserve existing entries. Do not reset the journal at the beginning of a run.
- Record a skipped run and its concrete reason. Do not relabel failed or skipped posts as published.
- Keep API keys, account tokens and private user data out of JSON inputs, captions, assets, logs and the repository.
